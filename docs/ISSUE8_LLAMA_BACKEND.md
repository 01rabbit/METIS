# Issue #8: experimental controlled llama-server boundary

`LlamaServerBackend` starts a pinned `llama-server` binary with a pinned GGUF and a private mode-0700 Unix socket directory. It never opens a TCP listener. The caller supplies SHA-256 hashes, a shared SQLite database, a stable budget key, a cumulative token limit, and a positive per-call output cap. A different hash or unavailable file prevents launch. The process is supervised and stopped at context exit; a failed completion request also stops it.

For each call, the backend asks the same live server `/tokenize` with `add_special=true`, atomically reserves prompt count plus `n_predict` under `BEGIN IMMEDIATE`, then calls `/completion` with bounded `n_predict` and `cache_prompt=false`. Reservations are never refunded, including interruption or timeout. It checks reported prompt and output counts, effective `n_predict`, model path, and output type before releasing content. The backend discards server stdout/stderr and does not write prompts, completions, candidates, or flags to its ledger.

This primitive is **not** yet connected to the fixture runner or advertised as a hard-cap capable provider (`hard_cap_capable=False`). A strict claim still requires adversarial integration tests of concurrent callers, tokenizer parity across prompt shapes and context limits, request timeout and crash handling, server versions and settings semantics, model replacement between hash check and open, caller cancellation, and cumulative accounting across all invocation paths. The current process pin checks before launch; an attacker able to mutate the model path afterward is outside this prototype's verified boundary. A trusted writable database and private host process space are assumed.

A read-only `ai-claude` review identified process cleanup, re-entry, and mismatch handling gaps; those paths were tightened and given synthetic tests. The review also noted that socket timeouts were per I/O operation. A monotonic deadline now covers `/tokenize` and `/completion` together; a daemon request thread permits supervisor-side termination even when bytes trickle. Synthetic slow-trickle tests cover expiry before and after reservation. A wedged operating-system thread can outlive this call until the killed socket unblocks, so this remains an experimental boundary.

## Threat boundary

The pinned paths and the SQLite database must be controlled by the trusted local operator. Hashes are checked before launch, but a local actor with write access can replace the binary or GGUF between verification and execution or model loading. A separate immutable artifact store, read-only permissions verified at open, or descriptor-bound loading is needed before claiming resistance to that race. The backend has no network listener and only connects to its own private Unix socket, but it does not sandbox the native server process. The capability flag remains false while these assumptions and full integration are unverified.

## Specialist adapter

`LlamaSpecialist` implements the existing `CodexRunner` turn interface for `run_assignment` and `autopilot`. Its constructor binds a catalog model ID to the pinned binary and GGUF hashes, a stable shared budget key, and the same SQLite database used by the scheduler. Each call starts one owned native process, asks for `DECISION_SCHEMA` JSON with no tools, and returns a `CodexTurn` with observed input/output token counts and `local_unix_socket` isolation metadata. Invalid model JSON still retains observed usage and is handed to the driver's existing decision rejection path. Images and a different model ID are refused before process startup. Cancellation is checked before, during, and after the model call; a live cancellation stops the process and keeps any reservation already made.

The scheduler's model-turn reservations remain a separate shared limit from this adapter's token reservations. Both must use the same run and database scope; `budget_key` is caller supplied and must be stable for all concurrent workers on that run. The held-out real-model path still rejects this runner because `hard_token_budget_enforced=False`. No CLI selection has been added, so an operator must construct and pass the adapter explicitly. The adapter's `local_unix_socket` metadata records process-level isolation only; it is not an OS sandbox.
