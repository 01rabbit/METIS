# Issue #8: experimental controlled llama-server boundary

`LlamaServerBackend` starts a pinned `llama-server` binary with a pinned GGUF and a private mode-0700 Unix socket directory. It never opens a TCP listener. The caller supplies SHA-256 hashes, a shared SQLite database, a stable budget key, a cumulative token limit, and a positive per-call output cap. A different hash or unavailable file prevents launch. The process is supervised and stopped at context exit; a failed completion request also stops it.

For each call, the backend asks the same live server `/tokenize` with `add_special=true`, atomically reserves prompt count plus `n_predict` under `BEGIN IMMEDIATE`, then calls `/completion` with bounded `n_predict` and `cache_prompt=false`. Reservations are never refunded, including interruption or timeout. It checks reported prompt and output counts, effective `n_predict`, model path, and output type before releasing content. The backend discards server stdout/stderr and does not write prompts, completions, candidates, or flags to its ledger.

This primitive is **not** yet connected to the fixture runner or advertised as a hard-cap capable provider (`hard_cap_capable=False`). A strict claim still requires adversarial integration tests of concurrent callers, tokenizer parity across prompt shapes and context limits, request timeout and crash handling, server versions and settings semantics, model replacement between hash check and open, caller cancellation, and cumulative accounting across all invocation paths. The current process pin checks before launch; an attacker able to mutate the model path afterward is outside this prototype's verified boundary. A trusted writable database and private host process space are assumed.

A read-only `ai-claude` review identified process cleanup, re-entry, and mismatch handling gaps; those paths were tightened and given synthetic tests. The review also noted that socket timeouts are per I/O operation rather than a strict whole-call deadline. This remains a limitation and is another reason the capability flag stays false.
