# 継続的なナレッジ取り込み

この経路は、著作物のコピーではなく、汎用的な事実・分析手法を独立して記述した
Markdownのレビューと反映に限定します。講座本文、記事、解答、コード、画像、動画、
スクリーンショット、検体、ケースログを直接取り込んではいけません。
翻訳、語尾変更、名称置換だけで新しい記述とみなすことも禁止します。

元リポジトリのファイルを実行せず、外部APIにも送信しません。変更検知で保存するのは
元パスのハッシュ、内容ハッシュ、サイズ等だけです。元本文・ファイル名はレポートへ
保存しません。生成した原稿とレビュー記録は .state/intake/ に置き、Git対象から外します。
元本文は、この私有フォルダーにもコピーしません。

## 実行方法

リポジトリのルートで実行します。SOURCEには元チェックアウトを指定してください。
元チェックアウトとMETISは別々のディレクトリに置いてください。同一ディレクトリ、
一方がもう一方の配下にある構成は拒否します。元資料を編集・更新する作業は、検査と
反映が終わるまで止めてください。採集の前後で一覧とファイル状態を比較します。

~~~bash
python3 -m metis.blue.runtime.knowledge_intake snapshot --source "$SOURCE" --out .state/intake/baseline.json
python3 -m metis.blue.runtime.knowledge_intake diff --source "$SOURCE" --baseline .state/intake/baseline.json --out .state/intake/delta.json
~~~

初回の基準点は作成済みの .state/intake/source-baseline.json です。
以後の差分は追加・変更・削除を別々に示します。削除された元資料に対応するMETIS資料を
自動削除することはありません。既存知識への影響をレビューしてください。

変更箇所は元リポジトリ側で読みます。候補原稿には説明を貼り付けず、必要な事実、
適用条件、誤判定条件、証拠の限界を自分の構成と言葉で記述します。元実装を利用したい
場合もこの経路でコードをコピーせず、要求仕様と振る舞いの確認から別途実装します。

独立した表現へ書き直す際も、分析に必要な具体性を失わせてはいけません。内容レビューでは
次の4項目を原資料・製品の一次仕様・取得済みschemaと照合します。

- 所在：製品・形式・版、既定PATH、収集元、実環境の設定から場所を解決する方法。
- 値：table/column、provider/EventID、field、型、エンコード、単位、epoch。
- 関係：joinキー、host/tenant/boot/sessionの適用範囲、重複・欠損・時刻差。
- 意味：その値から分かること、分からないこと、正常系、強い結論に必要な追加証跡。

正式な技術識別子は正確な綴りで記載します。長文一致を避けるためにPATHやフィールドを
分割・改変してはいけません。長い技術名が検査に触れた場合も、検査をすり抜けるための
書換えは行わず、一致の内容と独立性を再評価します。案件固有のホスト名・実パス・秘密・
答えと、再利用できる製品の既定パス・schemaは区別してください。

参照表は対応するSKILLから辿れる場所に置き、原資料の誤りを見つけた場合は根拠とともに
訂正します。未知の版や未検証レイアウトを確定値へ変えてはいけません。レビューした資料、
見つかった欠落、採用・保留した事実、対応先のhashを[技術棚卸し台帳](technical-retention.json)
へ記録し、関連する[具体値の評価](benchmark.md#technical-locator-regression)を再実行します。
機械検査の合格や見出しの一致は、この内容レビューを代替しません。

ファイル単位で案件記録・旧実装として除外しても、その中の汎用的な形式情報まで確認済みに
してはいけません。本文の転載は除外したまま、既定PATH・フィールド・単位・版条件の候補を
別に点検します。候補ごとに既存対応、独立追記、誤記訂正、案件固有として除外、未確認を
区別し、元の内容hashと実際に読んだ行・範囲を記録してください。検索hitや語彙の一致を
意味レビューの件数へ繰り上げず、候補箇所の確認と全文の確認も別々に数えます。

候補JSONの構造は次の通りです。sourcesの値はsnapshotの対応行から取得します。

~~~json
{
  "policy": "independent-lessons-v1",
  "changes": [{
    "target": "skills/soc-triage/references/new-lesson.md",
    "text": "# 独立して書いた説明\n\n適用条件と証拠の読み方。\n",
    "sources": [{
      "path_sha256": "元パスのハッシュ",
      "content_sha256": "元内容のハッシュ"
    }]
  }]
}
~~~

識別語の禁止パターンは環境変数METIS_DENY_PATTERNで外部から渡してください。
元提供者の識別語をMETISの設定・テスト・Git履歴へ保存しないための仕様です。
未指定では反映候補の検査を通しません。

~~~bash
python3 -m metis.blue.runtime.knowledge_intake check --source "$SOURCE" --draft .state/intake/draft.json --out .state/intake/review.json
~~~

checkは以下を検査し、問題があれば停止します。

- 元ファイル全体の一致、およびUnicode・大文字小文字・空白等を正規化した長文一致。
- コードフェンス、インデントされたコード形式、HTML、埋め込み画像等のメディア、
  長い不透明な符号化文字列。
- 外部指定の識別語、古い出典ハッシュ、重複した反映先。
- 絶対パス、親ディレクトリへの逸脱、シンボリックリンク、対象外拡張子。
- 読み取り中のファイル変化、ファイル数・バイト数上限への到達。

完全なレジストリキーは、それ自体が64文字の一致窓を超える場合があります。一致する全窓が
単一のinline literal内に収まり、認識対象のhiveから始まるキー表記である場合だけ、
`native_registry_review` にliteralのSHA-256を出します。これは自動承認ではありません。
担当者以外が完全なキーを一次資料・使用版・取得条件と照合し、案件固有値や散文ではないと
確認した場合に限り、通常の確認書に `native_registry_identifiers_are_factual: true` を追加します。
キーの外にまたがる一致、全文コピー、禁止識別語、コード・媒体の検査は省略しません。
現在の対象はHKLM/HKCU/HKUと対応する長いhive名の限定されたキー表記です。
その他の長い識別子を便宜的にキーへ偽装してはならず、対応外は停止して内容を再評価します。

`audit-library` はこの場合も生の一致を残してレビュー要求を報告します。公開する表現レビューでは、
機械検出件数と、対象hash・literal hash・一次資料・独立reviewを結び付けた判断を分けて記録します。
確認した事実の一致を「一致0件」へ数え直しません。literalの承認もOS/schema全体の検証を意味しません。

元ファイルは最大100,000件、1件16 MiB、合計64 MiBまでです。候補原稿は1回20件、
各128 KiBまでです。JSON入力は8 MiB以内です。上限を超えた入力を途中まで成功扱いに
することはありません。元パス一覧の取得も16 MiBで打ち切り、処理を停止します。

機械検査が通ってもレビューは必要です。長い一致を持たない翻案や、登録された元資料に
含まれない著作物までは判定できません。技術用語の一致も保守的に検出するため、検出を
回避する目的で文章を細切れにせず、内容と表現を改めて評価してください。
この仕組みは権利処理や独立著作性を自動証明するものではありません。
類似検査はUTF-8で読める元ファイルを正規化し、64文字の窓を16文字間隔で索引化します。
候補側は1文字ずつ照合するため、連続79文字以上の同一表現には必ず比較窓が含まれます。
短い引用、別の文字コード、翻案、索引にない資料まで「一致なし」で承認してはいけません。
非UTF-8資料にもファイル全体のハッシュ照合は行います。機械で見抜けないコードや
表現の取り込みは、責任者レビューで拒否してください。

## レビューと反映

責任を持つレビュアーが、原稿の独立した表現、事実・手法への限定、ケース情報・秘密の
不在、コード・メディアの不在、内容の正確性を確認します。
attestationにはreview全体の正規化JSONのSHA-256と以下を記録します。

- review_sha256、reviewer
- independent_expression: true
- facts_and_methods_only: true
- no_case_or_secret: true
- no_source_code_or_media: true
- scope_and_accuracy_checked: true

`native_registry_review` が空でない場合のみ、追加の
`native_registry_identifiers_are_factual: true` が必須です。不要な原稿では余分な項目として拒否します。

ハッシュ計算はPythonの metis.blue.runtime.knowledge_intake.sha(encoded(review)) と同じ方式です。
担当者名やチェック欄だけで権利上の判断が保証されるわけではありません。
同じOSユーザーの悪意ある操作を隔離するセキュリティ境界でもありません。

~~~bash
python3 -m metis.blue.runtime.knowledge_intake apply --source "$SOURCE" --draft .state/intake/draft.json --review .state/intake/review.json --attestation .state/intake/attestation.json --out .state/intake/receipt.json
python3 scripts/check_repo.py
~~~

applyは現在の元資料・原稿・反映先・禁止パターン・移行台帳・取り込み台帳・検査実装を
再検査し、レビュー時と異なれば反映しません。レビューJSONにも独立性の確認書にも
契約にない項目を追加しないでください。確認書は未記入の確認欄や余分な項目を拒否します。
排他ロックで同時反映を制限し、ファイルは書きかけが見えない形で差し替えます。
変更前後で元スナップショットと反映先を確認し、通常の書き込み失敗では元の状態へ戻します。
対象はskills/detections/playbooks配下のMarkdownのみです。Gitへ自動commit/pushしません。
反映した知識のハッシュは移行台帳へ更新し、出典ハッシュと反映内容のハッシュだけを
docs/intake-ledger.jsonへ記録します。原文やレビューの会話は追跡ファイルへ入れません。
レポートの出力先は .state/intake/ 配下のJSONです。入力ファイルへの上書き、シンボリック
リンク経由の書き込み、排他ロックや回復用ディレクトリへの出力は拒否します。レポートの
保存に失敗した場合も、取り込み台帳を確認してから再試行してください。同じ原稿を
二度適用することはありません。

## 中断後の回復

反映中は .state/intake/transaction/ に、METIS側の変更前ファイルと回復用ジャーナルを
一時保存します。元チェックアウトの原文を保存する用途ではありません。完了時に削除し、
プロセスが強制停止した場合は次のapplyを止めます。次のコマンドで状態を確認し、
コミット前の変更を戻すか、既に完了した反映の一時ファイルを片付けます。

~~~bash
python3 -m metis.blue.runtime.knowledge_intake recover --source "$SOURCE" --out .state/intake/recovery.json
~~~

回復は変更前・変更後のハッシュと退避ファイルの整合性を検証します。中断後に別の
編集者が同じファイルを変更していた場合は、その内容を上書きせず停止します。
担当者が競合を確認・解消してから再実行してください。ジャーナルを削除して反映を
強行しないでください。回復自身が中断しても再実行できます。

このロックはMETISの取り込み処理同士の調停です。他のエディターをロックする機能、
悪意ある同一OSユーザーを隔離する機能、ディスク故障時のバックアップではありません。
複数ファイルを一瞬で同時更新するデータベースのような読み取り隔離もありません。
反映・回復中は対象知識の利用を止め、完了後にcheck_repoを実行してください。
この排他・回復実装はPOSIX環境向けです。実プロセスの中断と回復はmacOSで検証しており、
Windowsや複数ホストから共有するファイルシステムでの同じ保証は未検証です。

元リポジトリ全体が更新された場合、過去の移行台帳は当時のスナップショットとして残ります。
新しい変更の有無はintake diffで確認します。全差分の採否レビューが済む前にbaselineを
上書きして「未確認変更なし」にしてはいけません。

## 既存資料の扱い

この仕組みの導入以前からある資料を自動承認しません。導入時に完全一致の9ファイルを
独立記述へ変更しました。その時点の長文類似検査では119資料中85件に一致があり、
表現レビューの対象としました。これは当時の記録であり、現在の件数は下記の再検査と
台帳で確認してください。元資料が自作か否かにかかわらず、今後の取り込みでは直接コピーを行いません。
対応状況は[技能の準備状況](skill-readiness.md)を参照してください。

~~~bash
python3 -m metis.blue.runtime.knowledge_intake audit-library --source "$SOURCE" --out .state/intake/existing-expression-audit.json
python3 -m metis.blue.runtime.knowledge_inventory --source "$SOURCE" --out .state/intake/structural-inventory.json
~~~

audit-libraryは一致のあるファイル名とハッシュだけを報告し、レビュー対象があれば
終了コード2で停止します。元文章や一致箇所は出力しません。通常のcheck_repoが通っても、
この表現検査に合格したことにはなりません。既存の一覧は
[表現レビュー台帳](expression-review.json)に記録しています。
knowledge_inventoryの見出し区分と関数数は棚卸しの索引です。意味を一件ずつ検証した
件数ではありません。元資料の削除・改訂と、METIS側の採否・更新を混同しないでください。
